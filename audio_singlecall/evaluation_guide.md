# Kairos Audio Evaluation Guide

This document explains the evaluation process for the Kairos audio pipeline, how to interpret results, and how system issues like OOM and storage are handled.

## 1. What are we doing in the evaluation?
The evaluation compares the **Single-Call Pipeline** (High Parallelism) against the **Original Pipeline** (Sequential). We measure how well the optimized pipeline preserves quality while improving speed.

### Key Metrics:
- **Speech Detection Accuracy**: A confusion matrix (TP, TN, FP, FN) comparing whether both pipelines detected speech in the same scenes.
- **Transcription Similarity**: Uses **Jaccard Similarity** (word overlap) to check if the Whisper output from the single-call method matches the original per-scene calls.
- **Natural Audio Accuracy**: Compares AST (Audio Spectrogram Transformer) labels to ensure environmental sounds (e.g., "dog barking", "music") are identified consistently.
- **Timing Efficiency**: Compares the wall-clock time of both methods to calculate the **Speedup** factor.

## 2. How do we get the evaluation results?
Results are generated by running the evaluation script:
```powershell
python -m audio_singlecall.evaluation --video "Videos/YourVideo.mp4"
```
The script:
1. Loads `checkpoint.json` from the `_processed/` folder (Original results).
2. Loads `audio_results.json` from the `audio_singlecall/results/` folder (New results).
3. Align scenes by timestamp.
4. Computes the metrics and saves them to `evaluation.json`.

## 3. Storage and OOM Handling

### Why do OOM errors occur?
OOM (Out-of-Memory) errors usually happen during **High Parallelism** processing of long videos. 
1. **Old Logic**: We were passing the *entire* audio buffer of a 30+ minute video to every parallel worker. If you had 4 workers, you had 4x the audio memory.
2. **Fix**: We now **slice** the audio buffer into small scene-specific chunks *before* sending them to workers. This ensures each worker only holds a few seconds of audio.

### Storage Management
- **Current Strategy**: We store intermediate artifacts (`.clips`, `.frames`, `.fps`) in the `_processed/` directory. These are essential for evaluation and debugging.
- **Cleanup**: In a deployment environment, these can be deleted after the final summary is generated. We have added a conceptual cleanup logic in `main.py`.
- **Freeing Space**: You can free space manually by deleting the `.clips` folder inside the video's result directory if you only care about the JSON results.

## 4. Why is ".CCTV Dogs" empty?
The `.CCTV Dogs` result shows 0 scenes and 0 seconds of Whisper/AST.
- **The Reason**: `PySceneDetect` (using `ContentDetector`) found **0 scene changes** because the video is a static feed. 
- **Negligible Audio**: The background "beeeee" or static is filtered out by our **Dynamic RMS Threshold**. Since the RMS level is below the `SILENCE_THRESHOLD_DBFS`, the system correctly identifies it as "no meaningful audio" and skips processing to save time.
- **Expected Behavior**: For a video with no visual or audio changes, an empty result is the correct "optimized" output.

## Titanic (3-hour) Readiness
For extremely long videos like Titanic:
- We have implemented a **Memory Check** that warns you if available RAM is below 2GB.
- The **Parallel Dynamic Chunking** logic in `whisper_singlecall.py` splits long audio into 10-minute segments, preventing the Whisper model from hitting memory limits.
